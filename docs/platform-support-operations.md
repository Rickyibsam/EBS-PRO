# EBS PRO platform support operations

## Ticket references and response targets

Every support case receives a sequential numeric reference. The database assigns the number; clients must not choose or edit it.

The first-response target is calculated when a case is created:

| Priority | First-response target |
|---|---:|
| Critical | 1 elapsed hour |
| High | 4 elapsed hours |
| Normal | 24 elapsed hours |
| Low | 72 elapsed hours |

These are elapsed-time targets, not a business-hours calendar. The ticket stores its target, first response timestamp, and latest customer/staff reply timestamps. Resolved and closed timestamps are maintained by the database.

## Attachments

Files use the private Supabase Storage bucket `platform-support-attachments`. Only PDF, JPEG, PNG, WEBP and plain-text files up to 10 MiB each are accepted. Object paths are scoped by ticket and uploader. Storage policies authorize access through either the active platform staff role or membership in the ticket's tenant. The metadata table is append-only for authenticated clients. A signed download URL is created only after the caller can read the private object.

Failed metadata writes may clean up only the uploader's unregistered object; registered attachments cannot be deleted through the client.

## Notifications

Database triggers create in-app notifications for new tickets, staff replies, customer replies, assignment and status changes. Supabase Realtime streams new notifications to the signed-in recipient. Each authenticated user can read only notifications addressed to their own user ID and can update only the `read_at` field. Notifications are generated by database triggers; clients cannot create or edit notification content.

## Website privacy and performance

The ERP is an authenticated business application, not a public marketing website. The application shell therefore sends `noindex, nofollow` metadata to avoid indexing private workspace routes. Public SEO landing pages, if needed later, should be hosted as separate public pages with their own indexable metadata.

The Vite build separates React and Supabase vendor bundles to improve browser caching. The PWA shell cache version is incremented when the static shell changes. The Super Admin browser audit checks the current page only; it is not a full-site crawl or a field Core Web Vitals measurement.

## Platform staff administration

Only an active Super Admin can provision or change platform staff. A staff member must already have a registered EBS PRO account with a confirmed email address. The staff role is either Super Admin or Support Admin; it is separate from tenant memberships and does not grant tenant financial access. The final active Super Admin cannot be demoted or deactivated, and concurrent staff-role changes are serialized. Staff changes are recorded in an immutable audit table. Passwords are never displayed; the portal can send a Supabase password-recovery email to a staff member.

## Escalation and resolution history

Support Admins can escalate an unresolved case to the Super Admin team with a mandatory reason. The database rejects escalation of resolved or closed cases, increments the escalation level under the ticket row lock, records who escalated it, appends an immutable ticket event, and creates a notification for active Super Admins. Ticket event history records creation, status changes, assignment changes, resolution edits and escalations. Tenant users can read history for their own company's tickets; only platform staff can read cross-tenant cases. Client sessions cannot insert or edit history events.

## Agent assignment

Active Super Admins and Support Admins are exposed to the internal agent picker through a server-authorized directory RPC. Ticket assignment is performed through a guarded RPC that rejects inactive or non-platform accounts. Assignment changes automatically create an immutable ticket-history event and notify the affected agent. Tenant users cannot access the platform agent directory.
